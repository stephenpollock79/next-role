# Next Role board — architecture

Last verified against: 28 Oct 2026.
If this doc and the code disagree, trust the code, then fix this doc.

The board is a Claude artifact in your own account: a multi-file page (`index.html`, `js/`, `css/`). Its data
lives in the artifact's database (read and write it with ArtifactData), not in the page code. Capabilities: db,
assets, sample, downloads; a publish that omits `capabilities` keeps them. `profile/settings` `board.url` holds
the board's own link, written at installation.

**A test board** is the same code published as a second artifact with its own database and
`profile/settings` `board.kind: "test"`: setup's Claude steps become dry runs, and How to use › Under the hood
offers Start again. Useful for trying setup without touching your real board.

## How to change the board (the fast way)

1. **Never read the whole board into context.** Find the right file below, then fetch only that file:
   Artifact `read` with `url` and `path: "js/12-interaction.js"` (it saves to disk). Use Grep on the saved
   files to find the spot, then Edit.
2. **Publish only what changed:** Artifact `publish` with `url`, `file_path` = `index.html`, and `files`
   listing only the changed files. Files you leave out are kept.
3. **Bump the cache key.** Every `<link>` and `<script>` in `index.html` ends `?v=YYYYMMDDx`. Change it to
   today plus a letter on every publish (one sed across `index.html`), or browsers may mix old and new files.
4. **Publish gate.** A new session must view the live version before its first publish. Read `index.html`
   (about 84 KB) rather than every file.
5. **Before publishing JS:** run `node --check` on each changed file. For anything beyond a small edit, see
   "Testing" below.
6. **Keep personal facts out of the code.** Names, city, employers, companies, people, job sites, pay floor
   and rule numbers belong in the board's data, never in the code or the skills: write neutral examples
   (Acme, `<rule id>`) instead. That keeps updates easy to merge, and your changes shareable.
7. **Revert:** republish the previous version of the changed files (the artifact keeps its publish history, and
   this repo has every version). The data is untouched.

## Navigation

Sidebar: **Overview · Roles · Week ahead · Insights** (no group heading; `data-grp="plan"`), then **Tools** (`data-grp="tools"`):
Sourcing · Search review · Targets · People · Warm routes · Compare · Mock interview · Data health, then About me · How to use (`data-grp="me"`). How to use's sub-tabs are **Start here** (default) · Set up · Running it (the loop diagram and one card per stage: You, Find, Decide/apply/interview, Learn, Tune) · **Pages** · **FAQ** · Under the hood, with a search box `#hp-searchbox` above them; the FAQ covers acting on Highlights. The phone section menu
(`12-interaction.js`: `syncTabSel` fills `#tabsel`, shown as the pill `#tabselbtn` and the sheet `#tabsheet`, `tabSheetOpen`/`tabSheetClose`) groups Planning · Opportunities (the stepper's stages) · Tools · About me. Insights keeps the tab id `pipeline`
(`#tab-pipeline`, `showTab("pipeline")`); Roles (`data-tab="roles"`) is not a tab of its own: `showTab("roles")` resolves to `rolesLanding()` — the first stage with something on you, else the first non-empty stage, else Longlist — and the Roles item stays selected on all five stage pages (`ROLE_TABS`, `paintRolesNav`); its badge `#tc-roles` is the sum of `funnelMine()`. The stepper in the top bar navigates the five stages; the phone menu leaves Roles out. Search review is `review` (`#tab-review`, `#rv-root`). Warm routes is `warm` (`#tab-warm`, `#wr-root`); 12's `showTab` doesn't list it, so 48's `showTab` wrapper shows and hides that section. Sourcing is `routine`, with sub-tabs **Auto sweep** (`data-k="channels"`: kind "auto" channel cards in `#ch-list`, then How the queue is built; its rail holds `#src-rail-status`, `#src-rail-runs`, the Cut by your rules card (`#screened-meta`, `#dropoff`, `#dropoff-note`, hidden `#screened-detail`/`#screened-list`)) and **Manual** (`data-k="manual"`: kind "manual" channel cards in `#ch-list-m`, with the Manual passes rail `#manual-passes` and `#src-rail-manual`). A strip `#src-strip` above the tabs counts both and links to Insights and Search review. One `channels` collection; the split is display only. Closed is `rejected`; People is `people` (its own Tools item; Targets' sub-tabs are only Companies and Sectors — `TARGETS` in `12-interaction.js`, switched by `[data-tsub]` in `#targets-nav`). Targets › Companies opens with a static fold `#co-ratehelp` (`details.corate`, in index.html, no JS): one line saying the rating decides how often the sweep reads each company's jobs page, and a table of what each rating does (Want it, Would consider, If it appears, Unrated, Ruled out); keep it in step with the sweep's rating table and `RATE_CAD`.

## Rules the split depends on

- **One shared global scope.** Every file is a classic script with `"use strict"`. Top-level `function` and
  `var` names are globals visible to every file. Never declare the same top-level name twice.
- **Load order matters for code that runs at load.** Top-level statements (listeners added, `x = …` lines,
  IIFEs) run as their file loads. They may only *call* functions or read `var`s from the same or an earlier
  file. Function bodies run later, so they can reference anything.

## Highlights design

This is the card map the code implements (js/19, js/27, js/28).

**Rules for a card**
- Every card needs a **signal** the board can count, a **breach** with a minimum amount of evidence, and an **action type**: **Fix the setup** (a rule, channel, search term or setting; Suggest a change drafts it), **Your move** (a behaviour change; the board recommends, nothing changes) or **FYI** (context that stops a wrong conclusion).
- Highlights are **patterns**: never a chore about one role (that's Waiting on you) and never a breakage (that's Data health).
- **A weekly top 6**, picked the first time the board opens each week (Monday-based): one card per area in this order: outcomes, supply, your decisions, the filter, foundations; plus the weekly screen-out check while it waits. A handled card drops off and isn't replaced until next Monday. Nothing outside the six is shown; Search review reads them all.
- **The user sets only their goals** (My targets). Evidence thresholds are fixed and never shown.

**My targets defaults** (`profile/prefs` `targets`): application band 5–10 live; new longlist roles a week 10; interview rate 20%; days to decide 7 / 7 / 5 (Longlist / Shortlist / To apply); long shots up to 50%.

**The map**
- **A. Is it running (Data health):** (1) a task failed or didn't run: latest `taskruns` per type past its usual gap + 1 day, or status failed; (2) ran out of room: the sweep's or a task's last 3 runs all `capped` with `left` not shrinking (with no `left` counts, three capped in a row); (3) a productive source went silent: nothing read (`read`, else `found`) in the last two sweeps from a source that averaged 3+ over the sweeps before (at least 2 of them); (4) a source can't be read: blocked or error on the last two sweeps, a Gmail error on an alert source, or no alert email reaching the sweep for two runs; (5) board errors: anything in `errlog` in the last 7 days.
- **B. The filter (Highlights):** (1) wrong roles reach the longlist: 3+ turn-downs in 14 days for a reason a deal-breaker should catch, per rule (or set of rules), counted since the rule last changed; at most 3 such cards (leak). Fix the setup. (2) Right roles screened out: the weekly screen-out check; 5+ checks with 1 in 5 wrong cuts since the rule last changed. Fix the setup. Once the week's check is answered, a rule with 3+ "worth revisiting" flags takes its slot (Decide). (3) One rule doing most of the screening out (10+ screen-outs, 35%+ for one rule): Fix the setup when it isn't tunable and one channel brings half or more of them, otherwise FYI.
- **C. Supply (Highlights):** (1) too few roles: new longlist roles in 7 days under the floor (once the board is 14+ days old), with the cause: market (FYI), rules or channels (Fix the setup); (2) too many to clear: arrivals over 1.5× decisions for two weeks with 20+ waiting (FYI); (3) poor channels: 8+ in, 20%+ of all roles and under half the average shortlist rate, or manual sites checked 2+ times with nothing in 4 weeks, or auto sources that read 5+ listings in each of their last 4 sweeps and passed none (`srcnofit`) (Fix the setup); best channel as good news; (4) stale terms or targets: a search term with no finds in 4 weeks (once 10+ roles carry a `searchTerm`), or 3+ watched companies with a readable board and no roles in 60 days (Fix the setup); (5) turned-down roles coming back: Data health › Duplicates.
- **D. Your decisions (Highlights):** (1) too slow: median days to decide at a stage over target, with 5+ decisions in 4 weeks (Your move); (2) closing dates missed: 2+ roles filled, pulled or expired while on the Shortlist or at To apply in 4 weeks (Your move); (3) "too strict" shows only through the band card's diagnosis.
- **E. Prep missing (Data health):** To apply for 2+ days with no CV draft; a booked interview in the next two days with no prep.
- **F. Outcomes (Highlights):** (1) outside the band: below says where the funnel is thin (To apply, Shortlist, Longlist pass rate, supply), above says hold (Your move); (2) poor mix: stretch bets over the limit (4+ scored roles from To apply on), weak Role Fit on live applications (half or more of 3+ live are Stretch or Low, at least 2) (Your move); (3) interview rate under target (8+ applications at least 14 days old), by Role Fit band (Your move); (4) lost at the same round type 3+ times (practise it in Mock interview), or the same "they said no" reason 3+ times (Your move); (5) replies to chase: Waiting on you, not Highlights.
- **G. Foundations:** needs something you don't have (3+), Highlights; data gaps, Data health.

**Dropped on purpose:** usage cost (the board can't see it), unused warm routes, CV quality (not measurable; shows up through F3), market as its own card (it's a cause on C1).

## Testing

How to test a big change: real data in a mock db, headless Chromium, live vs changed version compared on every
tab's rendered HTML and on 120 clicks. To do it: export the collections with ArtifactData
`list` + `out_dir` (include `screened`, `decided` and `runs` for Insights), serve `index.html` and the files
locally with a mock `window.claude.use("db")`, and diff against the live version. Small edits: `node --check`
and a look at the live board. The cloud workspace can't reach jsdelivr, so test Markdown preview by serving
marked and DOMPurify locally.
